Gitlab repositories hosted by DLR are used to manage the source code and configurations. This allows to regenerate any reference version from history. The repositories contain the complete set of configuration files for all used development tools, requiring no manual setup by contributors. The same configuration files are used regardless of whether tools are used locally or in CI/CD pipelines. The processor adopts the common semantic versioning scheme. The main branch of each Gitlab repository is protected, meaning developers are not allowed to push commits directly into it. Instead, they are expected to work on new features in dedicated branches and request via merge requests for their changes to be adopted in the main branch. Merge requests must pass the checks and tests inside the CI/CD pipeline prior to approval. Only maintainers (and higher roles) have permission to approve merge requests. Furthermore, maintainers are currently allowed to push directly to the main branch, but this is discouraged.

Software configuration files are delivered at each software delivery. A Configuration Item Data List (CIDL) is delivered at PDR, CDR and updated as needed, listing all the configuration data items including the status and version number.

\paragraph*{Design standards and verification}

The SW is designed to follow the ECSS-E-ST-40C [ECSS-E] with tailoring for the Copernicus expansion missions and follows object oriented programming methodologies. Design standards are defined in the SDD Section~4.7 and SDP Section~5.3. The automated CI/CD pipeline checks the adherence to the PEP8 coding standard, static analysis, and static type hinting. 

\paragraph*{Numerical accuracy}

The data type and precision of internal variables is defined in the \texttt{xarray.DataTree} (see SDD Section~5.5). Error handling (e.g. edge cases such as NaN data) described in the SDD Section~5.2. Regression testing is planned in the SIVVP, e.g. to verify that results remain numerically stable.

\paragraph*{Complexity, modularity and quality metrics}

To ensure modularity of the processor software, the input/output handling, core processing algorithms and orchestration of the value-adding modules wind, waves and currents is separated from the processor software into separate repositories L2O-IO, L2O-COREALG and L2O-VAM. These repositories are used by L2O-GPP, L2O-IPF and L2O-QC as needed. An \texttt{xarray.DataTree} with fixed structure provides an internal product format and defines the internal interfaces. This contributes to the processor modularity, as algorithms can be changed easily, while the data structure remains. The core processing modules EOPF-CPM implement a design that is compatible with the orchestration at the processing facility. COEREALG does not contain complex data structures, and is reused in GPP/IPF and QC and wherever needed. Program flow is designed together with the project team. Furthermore, the production model (PRODMOD) defines the processor input/output and the program flow, which is represented in the software design.

Code complexity is monitored as product metrics such as cyclomatic complexity and maintainability index. Furthermore, the test coverage is monitored by the CI/CD pipeline.

\paragraph*{Level of information of the design documentation}

The SDD and accompanying documents (e.g. ICD, IODD) detail the program flow as well as internal and external interfaces and dependencies. The structure and content follows the ECSS standard [ECSS-E].

Furthermore, docstrings are used for automated generation of an API reference. Docstring coverage and the number of comment lines are monitored by the CI/CD pipeline.

\paragraph*{Software design process}

A preliminary software design was discussed with ESA in the SRR. The software design was refined based on ESA's comments, the software requirements (including non-functional requirements), the production model and the needs for wind, wave and currents retrieval. The software design is engineered to facilitate testing using object oriented methodologies, the use of exchangeable core algorithms and the encouragement of the developers for test-driven development. Processor code is written in Python to ensure portability across operating systems and 64-bit hardware.

All Python code developed in the project follows the coding conventions defined by the PEP8 style guide. Adherence to these conventions is checked automatically on multiple levels of the development pipeline to catch deviations reliably and as early as possible.

The first level is the local development environment of contributors. The code repository contains a set of recommended extensions and settings for the most widely used IDE VS Code, such as linter, code formatter and static type checker. The intent is to help developers with setting up a development environment that provides immediate feedback to ensure adherence to coding standards as early as possible in the development flow. This is facilitated further by providing a set of Git pre-commit hooks that can be installed by developers to apply code checks automatically before each commit. This works independently of the IDE being used. Thus, evaluation of the coding standards is performed and fed back to the developers in parallel with the coding process.

The second level is the Gitlab platform. As the local development environment of contributors cannot be enforced, all committed code changes are checked by a suite of tools integrated in automated CI/CD pipelines on Gitlab. In combination with the branching strategy outlined in section \ref{subsec:methods-and-tools}, this ensures that only verified code enters the main branch. The code is put under configuration control only if the CI/CD pipeline finished without errors, including unit tests. A synthesis of the code analysis results (passed or failed) and corrective actions shall be reported in the SPAMR.

The automated code checks have already been implemented before the coding activities started, although some of the software used may have changed (e.g., flake8 was replaced by ruff). The following tools are implemented in Gitlab CI/CD, including some that are not related to Python code but check other file types:

\begin{itemize}
    \item Code checks, tests, and security
    \begin{itemize}
        \item ruff: Python code linter \& formatter
        \item mypy: Python static type checker
        \item radon-ci: Python code complexity analysis
        \item docstr-coverage: Python docstring coverage monitor
        \item bandit: Python code security scanner
        \item pip-audit: Python package dependency vulnerability checker
        \item pytest: Python unit and integration tests
        \item rstcheck: ReST file linter
        \item hadolint: Dockerfile linter
        \item trivy: Container image vulnerability scanner
    \end{itemize}
    \item Build and deliver
    \begin{itemize}
        \item build: Python packaging frontend
        \item setuptools: Python packaging backend
        \item twine: Python package uploader
        \item kaniko: Docker image builder
    \end{itemize}
    \item Documentation generation and upload
    \begin{itemize}
        \item sphinx: Documentation generation
        \item Gitlab pages: Web documentation hosting
    \end{itemize}
\end{itemize}

A tool for the measurement of "number duplicated lines of code" has not been implemented yet.

Milestones for software delivery and acceptance are provided in the [SoW]. Each software delivery is comprised of a development kit, runtime kit, and verification kit. The content of the software delivery kits is detailed in the SRS. Here is a checklist:

\begin{itemize}
    \item Software development kit
        \begin{itemize}
            \item source code (tarball)
            \item nominal processor configuration files
            \item configuration files for development tools, software checking tools (pre-commit hooks, CI/CD pipeline, etc.)
            \item license file (\texttt{LICENSE})
            \item copyright attribution at the end of \texttt{README.rst}, and in source files if source code cannot be associated to a single copyright owner
            \item credits in the \texttt{CREDITS} file for reused software
            \item API documentation (searchable HTML)
            \item software build instructions (as part of the software user manual)
            \item software reuse file (as part of the software user manual)
            \item Package dependencies for offline installation
        \end{itemize}

    \item Software runtime kit
         \begin{itemize}
             \item binary conda package (wheel format is acceptable for PDR as agreed with ESA)
             \item support and configuration files to run the software
             \item for each included software package: license file, including also the license of embedded SW, copyright attributions and credits as requested by the licenses of the re-used SW 
             \item Package dependencies for offline installation
         \end{itemize}

    \item Software verification kit
        \begin{itemize}
            \item Test configuration files
            \item Test datasets, incl. auxiliary data
            \item Set of tools to perform verification and acceptance testing, including quality tools (to verify different aspects of the scientific quality of the products) and tools for automated checks (e.g., for product format checking, or for executing test to cross check output of current release vs reference one)
        \end{itemize}

    \item General
        \begin{itemize}
            \item ensure that source code and binary packages correspond to each other
            \item ensure that all agreed changes are implemented
            \item ensure that all software problems are either resolved or declared
            \item adhere to the semantic versioning scheme
            \item SHA-256 integrity checksum, as available on the Gitlab release pages and Pypi
            \item it shall be possible to install, build and execute the SW and its environment offline
            \item version-pinned dependencies (e.g. requirements.txt)
            \item if dependencies from non-standard (i.e., other than PyPI, conda) repositories are used, these shall be provided both as source archives and also as binary packages in the selected packaging format (wheel or conda). 
        \end{itemize}
\end{itemize}

Planning and assurance of the software acceptance will be added to the SIVVP and SPAP at CDR, covering the following:

Software problem reports shall contain the following information:
\begin{itemize}
    \item identification of the software item;
    \item description of the problem;
    \item recommended solution;
    \item final disposition;
    \item modifications implemented (e.g. documents, code, and tools);
    \item tests re-executed.
\end{itemize}

In this project, software problems encountered during software verification and validation shall be reported as "Issues" in the Gitlab repository of the respective SW item, including a detailed description of the problem and, if possible, a recommended solution. The issue should be assigned to a responsible person. The assignee shall describe the problem resolution and report implemented modifications (documents, code, tools) in commit messages and link the merge request to the issue. As configured for the Gitlab repositories, the merge requests automatically trigger the execution of the CI/CD pipeline.
