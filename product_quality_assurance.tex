\subsection{Product metrics}
\label{subsec:product-metrics}

Based on the SRS and the quality model introduced in Section~\ref{subsec:quality-models}, the following product metrics are introduced and automatically checked in the CI/CD pipeline. The metrics are permanently stored as pipeline reports on Gitlab. The results of metrics collection and analysis are included in SPAMR reports, for each of the software items L2O-GPP, L2O-IPF, L2O-IO, L2O-COREALG separately.

%%%

\subsubsection{Unit test coverage}

The unit test coverage measures the fraction of the program code which is executed during unit tests. It is measured using \texttt{pytest} as a single value for each repository.

\textbf{Target:} 100\,\%, as given by L2O-RAM-0860

%%%

\subsubsection{Adherence to coding standards}

Adherence to coding standards is checked by a combination of linting, automated formatting and static type checking (\texttt{ruff check/format, mypy}). If no error is found, the result is \texttt{PASSED}.

\textbf{Target:} \texttt{PASSED}, as given by L2O-RAM-0900

%%%

\subsubsection{Source lines of code across repository}

Compute the number of source lines of code across the whole repository using \texttt{radon} as: SLOC = (total number of lines of code) – (comment and blank lines)

\textbf{Target:} No target value provided (see L2O-RAM-0960). The metric is both informative for monitoring the progress and required to evaluate the maintainability index.

%%%

\subsubsection{Comment lines of code across repository}

Compute the number of comment lines of code across the whole repository using \texttt{radon} as: CLOC = (total number of lines of code) – (source and blank lines)

\textbf{Target:} No target value provided (see L2O-RAM-0960). The metric is both informative for monitoring the progress and required to evaluate the maintainability index.

%%%

\subsubsection{Source lines of code per file}

Compute the number of source lines of code per file using \texttt{radon} as: SLOC = (total number of lines of code per file) – (comment and blank lines)

\textbf{Target:} $\leq 1000$ as given by L2O-RAM-0990. The result is \texttt{PASSED} if all files meet the target.

%%%

\subsubsection{Source lines of code per method/function}

Compute the number of source lines of code per method/function using \texttt{radon} as: SLOC = (total number of lines of code per method/function) – (comment and blank lines)

\textbf{Target:} $\leq 100$ as given by L2O-RAM-1000. The result is \texttt{PASSED} if all methods/functions meet the target.

%%%

\subsubsection{Number of duplicated lines of code}

Compute the total number of duplicated lines of code. This metric is not implemented yet, as it is not produced by \texttt{radon}.

\textbf{Target:} No target value provided (see L2O-RAM-0960). The metric is informative for monitoring the software maintainability

%%%

\subsubsection{Cyclomatic complexity}

This metric is an indicator for the code complexity. It measures the number of linearly independent paths through the code and is calculated using \texttt{radon} (see \url{https://radon.readthedocs.io/en/latest/intro.html}). The reported metric is an average across the repository.

\textbf{Target:} $\leq 10$ as given by L2O-RAM-0970

%%%

\subsubsection{Maintainability index}

This metric measures the maintainability of the source code. The maintainability index is derived from Halstead volume, cyclomatic complexity, number of Source Lines of Code (SLOC) and the percentage of comment lines using \texttt{radon} (see \url{https://radon.readthedocs.io/en/latest/intro.html}). The reported metric is an average across the repository.

\textbf{Target:} $> 50$ as given by L2O-RAM-0980

\textbf{Note:} As agreed, Halstead metrics are computed and logged by the CI/CD pipeline, but are not reported separately. The Halstead volume is used only internally to derive the maintainability index.

%%%

\subsubsection{Docstring coverage}

This metric measures the docstring coverage of functions, classes, methods and modules using \texttt{docstr-coverage}. The reported metric is an average across the repository, obtained by dividing the number of existing by the number of expected docstrings, expressed as a percentage.

\textbf{Target:} 100\,\% (no requirement)


\subsection{Timely metrication programme}
The product metrics are automatically computed and evaluated in the CI/CD pipeline. Merge requests must pass the checks and tests inside the CI/CD pipeline prior to approval. Only maintainers (and higher roles) have permission to approve merge requests.

\subsection{Product metrics analysis}
The product metrics are saved on Gitlab as CI/CD reports for each commit to the main branch. The status of the metrics are presented in the regular SPAMR reports at each milestone, and in progress meetings if considered relevant by the product assurance team. The regular analysis ensures that the product meets the quality requirements.

\subsection{Feedback to the development team}
The main branch of the Gitlab repository is protected, meaning developers are not allowed to push commits directly into it. Instead, they are expected to work on new features in dedicated branches and request via merge requests for their changes to be adopted in the main branch. As indicated, merge requests must pass the checks and tests inside the CI/CD pipeline prior to approval. This ensures that the immediate product quality is not degraded by individual commits. Degradation of the product quality which happen on a longer time scale (e.g., docstring coverage), is analyzed by the SPAMR reports.

As most of the metrics are also evaluated per file/method/function where applicable, shortcomings in individual parts of the software can be traced back to the respective software developer. The software developers are approached by the software product assurance team if necessary. In CI/CD, code quality issues are raised automatically for files/methods/functions which exceed any of the monitored metrics' thresholds, providing immediate feedback to the developers.

\subsection{Documentation quality requirements}

Documentation (e.g. software user manual, software reuse file) and reports (e.g. SPAMR) shall follow the structure and content of ECSS with tailoring. Deviations from the structure (i.e. table of contents) are allowed if another structure is better suited for the audience, e.g. in the software user manual. The documentation shall be unambiguous with consistent terminology. Documentation of python code is covered by docstrings with automatically generated API references and comments following PEP8 standard. 

\subsection{Assurance activities meant to ensure that the product meets the quality requirements}

As outlined in the previous sections, the product metrics are evaluated and reported regularly, and provided as direct feedback to the development team in order to ensure that the product meets the quality requirements.
